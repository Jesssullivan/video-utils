### Why video-utils departs from the estate on two rule sets

Measured from the rule sources, not from a run:

- **`aspect_rules_js` 3.5.1 instead of 2.9.1.** `web/` uses pnpm `11.25.0`
  (estate: `10.13.1`). For a lockfile version 9, rules_js 2.9.1 and 3.5.1 both
  `fail` in `_verify_lifecycle_hooks_specified` unless pnpm's build-script
  allowlist is declared. 2.9.1 reads only `onlyBuiltDependencies`; pnpm 11
  replaced that list with the `allowBuilds` map, which rules_js reads from 3.1
  (`npm/private/npm_translate_lock_state.bzl`: "pnpm 11 replaced
  onlyBuiltDependencies (a list) with allowBuilds (a dict…). Support both.";
  absent in v3.0.3, present from v3.1.2). 3.5.1 also carries pnpm `11.25.0` in
  its own version table and handles the pnpm 11 lockfile forms. 2.10.0 and
  3.0.0/3.3.0 are yanked on BCR; 3.5.1 is not.
- **`aspect_rules_ts` 3.10.1 instead of 3.8.4.** 3.10.1's version table carries
  TypeScript `6.0.3` with the same integrity as `web/pnpm-lock.yaml`
  (`sha512-y2TvuxSZ…`); 3.8.4's table stops at `5.9.3`. It declares
  `aspect_rules_js >= 2.0.0`, so 3.5.1 satisfies it (both
  `compatibility_level = 1`).

Either choice still needs one root-owned line: `web/pnpm-workspace.yaml` has no
`allowBuilds` (or `onlyBuiltDependencies`) key today, so the `@npm` repository
cannot be created until root adds `allowBuilds: {}`. That is recorded as a root
change request; it affects only `//web/...`.

- **`rules_rust` 0.70.0.** It is the BCR release whose `DEFAULT_RUST_VERSION` is
  `1.95.0` (0.69.0: 1.93.1; 0.71.3: 1.96.1; 0.74.0: 1.98.0), i.e. the channel in
  `rust-toolchain.toml`, so the toolchain checksums for that exact version ship
  with the rule set.
- **`rules_python` 1.8.3.** The estate version (tinyland.dev), already combined
  there with `rules_nodejs` 6.7.3 and `aspect_bazel_lib` 2.22.5 on Bazel 8.

Measured on the authoring host (section 9): this combination resolves on Bazel
8.2.1 and builds and tests the Rust crates and three Python test modules.

## 5. How estate repos build a SvelteKit app (S)

Two different answers exist:

- **xoxd.ai:** "The canonical site build is `pnpm run build`; Bazel is the only
  carrier for the in-house packages." Its root `BUILD.bazel` only calls
  `npm_link_all_packages(name = "node_modules")`. Each `inhouse/<pkg>/BUILD.bazel`
  re-packages a registry module with `npm_package(srcs = ["@<module>//:pkg"], …)`
  and `just inhouse-link` materialises it for pnpm; `package.json` carries
  `file:inhouse/<pkg>` specifiers.
- **site.scaffold:** "Just is the operator entrypoint; these finite Bazel
  targets own local and CI build, check, test". The root `BUILD.bazel` has
  `js_run_binary(name = "sveltekit_types", out_dirs = [".svelte-kit"])` running
  `svelte-kit sync`; `copy_to_directory(name = "app_workspace", hardlink = "off")`
  over sources plus generated types; `js_run_binary(name = "build",
  out_dirs = ["build"], patch_node_fs = False)` running a wrapper that copies the
  declared workspace to scratch, symlinks `node_modules` and runs `vite build`;
  and `js_test(name = "svelte_check_test")`. `just build` is
  `bazelisk build //:build` followed by a materialise step.

**Decision (I):** `web/BUILD.bazel` follows site.scaffold's target shape
(`sveltekit_types`, `app_workspace`, `build`, `svelte_check_test`) with one
runner script, while `pnpm build`/`pnpm check` remain the accepted gates as in
xoxd.ai. The differences from site.scaffold: the app lives in `web/` rather than
the repository root (so the actions use `chdir = package_name()`), and the
adapter is `adapter-node` with a fixed `out: 'build'`, which the runner copies to
the declared output.

## 6. How estate repos link registry packages (S)

One pairing, stated in site.scaffold and in the `xoxd_spectrogram` module docstring:

```starlark
bazel_dep(name = "xoxd_spectrogram", version = "0.1.0")                     # MODULE.bazel
npm_link_package(name = "node_modules/@xoxd/spectrogram",
                 src = "@xoxd_spectrogram//:pkg")                           # consumer BUILD.bazel
```

site.scaffold lists the linked labels in `TINYLAND_HOUSE_PACKAGES` and adds them
to the app's npm package list; `package.json` "intentionally carries no
first-party specifiers". First-party packages are Bazel/Bzlmod artifacts, never
npm specifiers (repo-contract skill, package-resolution row). The resolution
oracle is `bazel mod graph` / `bazel query`; a text or structural check is
inventory, not proof of an edge.

## 7. Remote cache (S)

- xoxd.ai: "GloriousFlywheel v4 has no checked-in remote profile: no endpoint…
  builds here use the disk cache only." `build --disk_cache=~/.cache/bazel-xoxd`.
- site.scaffold: `--remote_cache` (and optionally `--remote_executor`) are passed
  on the command line by `scripts/gloriousflywheel-bazel.sh` from validated
  environment; the checked-in `.bazelrc` holds only endpoint-free `ci-cached`
  behaviour flags and `try-import %workspace%/.bazelrc.flywheel`.
- tinyland.dev: the same rule ("Keep endpoint coordinates out of .bazelrc"),
  with a `gf-reapi-cell.gf-rbe.svc.cluster.local` credential helper, i.e. an
  in-cluster endpoint.

**Decision (I):** video-utils configures **no** remote cache, executor or BES:
a local disk cache only, and `tools/bazel/run.py` refuses those flags. A machine
that has a cache can add it in the untracked `user.bazelrc`.
