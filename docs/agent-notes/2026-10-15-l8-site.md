## Findings

1. The first draft of the `DEPLOY.md` state paragraph named the tracker issue and said "pull request". Both match
   the site's `internal-tracker-reference` leak rule, and the source scan failed (findings 2, then 1). The
   paragraph now names neither. Gate 5 caught this before any commit.
2. `test_v10_privacy_scan` fails in a linked worktree whose primary checkout has no `artifacts/runs`: the test
   requires `digests["checked"]` whenever the tree is a worktree, but `private_run_digests` only counts roots that
   exist. Hosted CI checks out a plain clone with no run directory, so the assertion is not reached there.
   Suggested fix (not applied; not a lane-owned file): guard the assertion on an existing runs directory.
3. One full-module run had one axe scan (status, w1280, light) report `target-size` on 13 nodes. The trace shows
   the stylesheet and five script requests to the loopback server failed with `net::ERR_NETWORK_CHANGED`, so the
   page was scanned unstyled. This was a host network event, not a site change. The previous full run and the
   separate gate 8 run both had 0 violations. If it recurs on a hosted runner, the fix belongs in
   `site/e2e/support.ts` (fail or retry a visit whose stylesheet did not load), not in the baseline.

4. The `inhouse-link.mjs` Bazel run rewrites one `usagesDigest` (the rules_nodejs `node` extension) in
   `MODULE.bazel.lock`, the same drift the L7 receipt records. This is not local only (corrected after review):
   on the hosted runner every `nix develop` after the link step logs that the git tree is dirty, so the site job
   evaluates a dirty flake tree (the dev shells do not read the tree's source, so the shells are unchanged).
   Locally `git diff --stat` after the link showed `MODULE.bazel.lock | 2 +-`; it was reverted and is not
   committed. The site job now checks tracked-file drift after the link: `MODULE.bazel.lock` warns, any other
   file fails. The bazel job keeps `--lockfile_mode=error` on the committed lock.
