## Intent and fixed interface

Complete the existing authoring-to-restoration loop by applying one existing, hash-pinned `authored_unrendered` capture profile through the same media restoration/export functions. No alternative DSP, direct profile object, extra controls, arbitrary filters/executables, URL, inherited take identity or expected-score claim is accepted.

```text
python scripts/apply_capture_profile.py INPUT
  --authoring-dir AUTHORING_DIR --receipt-sha256 RECEIPT_SHA256
  [--timeout-seconds INTEGER]
```

Proposed later typed fields are exactly `input`, `authoring_dir`, `receipt_sha256`, optional `timeout_seconds`. There is no hook change in this prototype lane. Input is the exact original named by the current parent baseline. Authoring directory is one fresh `RUN_DIR/capture-profiles/ID/` containing `receipt.json` and `profile.json`; the receipt hash comes from the already returned tool-25 authoring result. Relative paths are allowed only without traversal/symlink components. Paths are data, never shell commands.

Worker deadline is 1–600 seconds (default 600), and media FFmpeg/filter threads remain two. JSON inputs/results/receipts stay bounded. All validation completes before media subprocess launch.

## Existing restoration and atomic candidate output

Copy the verified profile bytes into an owned private ignored workspace. Invoke the existing `media.clean` and `media.export` functions with fixed paths and a remaining-time subprocess budget. The existing captured preroll, calibrated afftdn delay, pure denoised/residue outputs, optional EQ/compression stage, native sample extent, loudness normalization and copied-video/AAC verification are reused without changing their defaults or algorithms.

Only the new application runner replaces the media module's subprocess function during its scoped invocation; the frozen file stays unchanged. Each existing media command starts an owned POSIX session, with file-backed stdout/stderr and a 4 MiB per-stream refusal ceiling, at most 128 process receipts. Before group signals, inspect live PGID/SID membership; TERM/KILL cleanup reaps the direct leader and verifies no runnable same-session group member. A leader that exits while descendants survive still triggers cleanup. An inspection failure always attempts direct-child termination/reaping and returns `cleanup_failed` with descendant absence explicitly unverified. This is same-session group cleanup, not containment of deliberately escaped sessions.

Each process inspection is capped at three seconds. A timed-out observation may retry once using only the remaining allowance; ownership mismatches never retry. Observations leave0.25s for direct reaping when available. Initially empty groups may avoid a redundant postwait scan only when the exact leader was already terminated before observation and its direct wait succeeded; record that verification method. All inspections, polls, direct-child wait and inspection-failure fallback share one absolute five-second cleanup budget, so repeated inspections cannot restart the allowance. Stage budgets reserve up to five seconds (half remaining time for very short budgets) before the nominal whole-job deadline. Bounded cleanup temporarily protects only this worker's matching one-shot alarm, so it can reap an owned child after an interruption; external timers/handlers are not disabled. Cleanup may need up to five seconds of exceptional grace after an asynchronous outer interruption and is not a strict real-time execution guarantee. Real media timing/resource qualification remains root's subsequent gate. These semantics follow [Python subprocess](https://docs.python.org/3/library/subprocess.html) and [owned-group OS interfaces](https://docs.python.org/3/library/os.html#os.killpg).

Keep the whole candidate private until input rechecks and generated native extent/timeline/source/export checks pass. Do not overwrite original, profile, parent run, current master, latest pointer or another output. Failed validation launches no DSP. A postcommit reporting interruption retains that exact immutable run; its failure receipt is `failed_reporting_committed_candidate_retained` with `candidate_publication: committed_unreviewed` and the full previously prepared success outcome. It never deletes the committed run or claims absence. The owned processing alarm is disarmed once commit is recorded and before console reporting. This does not adopt a master or establish listening acceptance.

Compact successful output identifies `rendered_unreviewed`, evidence `source_bound_capture_profile_application`, candidate run/manifest/application receipt/export paths and hashes, original/profile/authoring identities, native capture bounds, `listening_accepted: false` and `master_adopted: false`.
